# Nature Dex 开源维护项目设计

## 目标

把“去大自然里 / Nature Dex”整理为一个可公开阅读、可本地运行、可持续维护的自然物种识别与个人自然档案开源项目，并为 Codex for Open Source 申请提供真实、可核验的项目维护证据。

## 项目定位

Nature Dex 是面向自然观察者的微信小程序：用户拍摄或导入自然照片，在明确同意后进行物种识别，并将确认后的观察保存为个人自然档案和物种卡片。识别结果始终需要用户确认；低可信、未知或识别失败的照片保留人工处理路径，不伪造成功结果。

开源项目的核心价值是：

1. 可替换的物种识别适配器和清晰的数据契约。
2. 隐私优先的照片处理、确认和删除边界。
3. 可复现的本地 mock 运行、测试和微信小程序体验。
4. 面向维护者的云函数、部署、故障处理和贡献文档。

## 公开范围与私有范围

公开：

- 根目录原生微信小程序源码与 `native/` 运行代码。
- `cloudfunctions/` 中不含凭据的云函数源码和各函数依赖说明。
- 服务契约、mock 适配器、测试、README、贡献指南、安全政策和发布记录。
- 已确认拥有授权或可公开使用的示例数据与资源。

不公开：

- API key、云环境 ID、生产数据库配置、私有域名和部署凭据。
- 用户照片、个人笔记、账户标识、私有生成图片和本地备份。
- 没有来源或授权记录的图片、字体、模型和第三方素材。
- `project.private.config.json`、运行时 `.env` 和生成的上传压缩包。

## 技术边界

- 微信小程序原生入口是发布源；历史 `src/`、`dist/` 和 Taro 实验不作为发布入口。
- 百度识别通过独立适配器接入；本地运行默认使用 mock，不要求开发者拥有供应商账户。
- 百炼相关科普和手绘能力必须由用户主动触发，并以可替换服务接口表达。
- 客户端不保存或上传照片，除非用户明确同意当前操作；云函数必须校验用户身份和任务归属。
- 识别是候选结果，不是医疗、保护等级或法律结论；需要把不确定性显示给用户。

## 质量与维护证据

首个公开版本必须具备：

- 新开发者可按 README 完成本地安装和 mock 流程。
- 静态检查、单元/契约测试和微信文件编译通过。
- 没有硬编码凭据，私有配置有示例文件和说明。
- 明确的 LICENSE、CONTRIBUTING、SECURITY 和隐私说明。
- 至少一条可复现的识别样例流程，以及未知/低可信/失败路径测试。
- 版本标签和变更记录。

后续维护以真实 Issue、代码审查、测试修复、适配器改进和小版本发布为主，申请材料只陈述已经发生并可由仓库记录验证的工作。

## 申请策略

申请仓库使用 Nature Dex 的公开 GitHub URL。申请中说明本人对项目的维护角色、项目的自然观察价值、公开使用和维护计划，并具体说明 Codex 将用于：

- 识别契约和云函数的代码审查。
- 隐私边界、权限校验和安全回归。
- Issue 分类、错误复现和测试补充。
- 微信构建、版本发布和维护文档。

不把本地 Codex 对话、生成过程或未验证的产品愿景作为项目采用证据。

## 验收标准

1. 仓库可公开发布，且敏感扫描无凭据命中。
2. 新开发者能够不配置真实识别服务运行 mock 流程。
3. 识别、人工确认、未知结果、删除和失败重试都有测试或明确限制说明。
4. 云函数部署需要的密钥和环境变量均通过文档说明，不进入版本库。
5. README 能准确区分已实现、需要云服务、需要微信控制台配置和未来计划。
6. Git 历史从公开基线开始，后续维护可通过提交、Issue、PR 和 release 核验。
