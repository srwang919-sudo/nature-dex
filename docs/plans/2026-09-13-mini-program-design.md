# 去大自然里微信小程序设计

## 目标

把现有 Taro 小程序从“可点的演示样机”变成可在微信内顺畅体验的本地观察收藏版：用户拍下或选定一张照片，主动开始鉴别，核对结果后获得一张以该照片为主体的收藏卡。

本期不承诺真实物种识别、云端账户、跨端同步、赠送/交易或正式发行。演示结果必须明确标识，不得把预设物种说成照片识别结果。

## 已确认的产品原则

- 保留 iPhone/Android App；微信小程序是独立的轻量入口，不用 WebView 承载原 App。
- 拍照只是获取照片；“开始鉴别”是独立的、用户主动触发的动作。
- 照片贯穿草稿、鉴别、揭晓、卡面和收藏，不以系统图库照片冒充用户实拍。
- 无法识别时保留草稿，允许重试、返回或手动选择；不自动生成卡片。
- 卡片保留 5:7 收藏比例和正背面信息；小程序首期以 CSS 透视倾斜、点按翻面和材质光泽替代高成本 WebGL Three.js。
- 系统“减少动态效果”或用户关闭动效时，直接显示卡片、关闭光扫和回弹，不妨碍翻面与阅读。
- 所有数据先存本机；清空仅作用于本机演示数据，不能伪装为线上账户注销。

## 方案比较

### A. 原生小程序卡片交互（采用）

用 Taro 组件、CSS transform 和本机存储实现相机、照片草稿、鉴别确认、揭晓和卡片。优点是加载快、可离线运行、权限与分享流程符合微信习惯；缺点是光效不如完整 3D 引擎自由。

### B. WebView 复用 App 的 Three.js 场景

开发量较小，但需要已备案的业务域名，微信内加载与手势表现依赖网络，也让相机和照片权限在两层环境间穿行。不采用。

### C. 小程序 WebGL / Three.js

微信确实提供 WebGL Canvas 与 Three.js 适配可能性，但需要真机性能、基础库兼容和包体积验证。留作本期交互稳定后、确有视觉差距时的增强项，不阻塞首版。

## 用户路径

```
首页“去观察”
  → 拍照 / 相册选图
  → 照片确认（可重拍、重选、删除草稿）
  → 开始鉴别
  → 演示候选结果 + “本地演示，需人工核对”
  → 确认物种
  → 封卡揭晓（低动效直接跳过）
  → 可拖动倾斜、点按翻面
  → 保存至收藏册 / 查看详情
```

未知结果路径：鉴别完成后显示“暂未确认”，保留照片草稿，提供“重试”“手动选物种”“返回”，不写入收藏。

## 数据模型与存储

新增 `ObservationDraft` 与 `CollectedCard` 两类本地记录，统一放进 `src/utils/storage.ts`。

```ts
export type ObservationDraft = {
  id: string
  photoPath: string
  createdAt: string
  source: 'camera' | 'album'
  status: 'ready' | 'identifying' | 'unknown' | 'confirmed'
  candidateId?: SpeciesKey
}

export type CardFinish = 'standard' | 'holo' | 'alt' | 'numbered'

export type CollectedCard = {
  id: string
  draftId: string
  speciesId: SpeciesKey
  photoPath: string
  createdAt: string
  finish: CardFinish
  revealSeen: boolean
}
```

用 `Taro.saveFile` 持久化临时照片；保存失败时留在确认页并明确提示，不创建半张卡。记录只存路径和必要元数据，避免在 1MB 同步存储配额中存 Base64 图片。进入收藏页前过滤掉路径不存在的坏记录。

本期演示鉴别由可注入的 `identifyDemo(draft, selectedTarget)` 返回结果，候选页清楚写明“本地演示”。真实服务未来替换此函数，接口保持 `IdentifyResult` 形状，避免重做页面。

## 页面与组件边界

| 单元 | 责任 |
|---|---|
| `pages/viewfinder` | 取图、照片确认、开始鉴别、未知/候选处理；不直接生成卡片 |
| `utils/observations` | 保存照片、草稿生命周期、演示鉴别、确认后原子创建收藏卡 |
| `components/CollectibleCard` | 5:7 正面/背面、材质主题、拖动倾斜、点按翻面、低动效 |
| `pages/reveal` | 封卡揭晓与卡片保存完成后的引导 |
| `pages/card` | 从收藏记录读取实拍卡；仅无记录时才展示原型资料卡 |
| `pages/home` | 用收藏记录驱动进度与卡片网格，而非硬编码物种集合 |
| `utils/storage` | versioned keys 与本机数据读写；不承载图片本体 |

## 卡片视觉与交互

- 正面：用户照片为主图；深色信息带承载中文名、学名、观察日期、工艺和“用户实拍 / 本地演示”。
- 四种工艺仅改变边框、光泽和标识；卡片正面不把保护级别做成夸张收藏稀有度。
- 背面：观察档案、栖息信息、保护提示（如适用）与本地演示标识。
- 手指左右/上下拖动时，以有限角度改变 `rotateX/rotateY`；松手回正；移动阈值内的轻点翻面。
- 以显式“看背面/看正面”按钮保证可发现性和无障碍操作。

## 失败处理与隐私

- 用户取消相机或相册：无提示或轻提示，保持当前页面。
- 相册/拍照/保存失败：显示可理解错误和“重试”，不改写已有收藏。
- 未知结果：仅留草稿，不能默认选择“翠鸟”等任何物种。
- 删除草稿要同时删除 `saveFile` 的本地副本；删除收藏卡不删除原始照片前要求明确确认。
- 微信分享本期仅生成物种资料卡或分享路径；不得默认上传用户照片。含用户照片的分享留到获得同意、云存储和审核规则后再做。

## 验收标准

1. 真机拍摄一张照片后，照片进入确认页，点击“开始鉴别”之前不会显示识别结果或生成卡。
2. 确认候选后，揭晓和收藏页使用同一张实拍照片；重新打开不重复抽工艺或播放强制揭晓。
3. 选择“未知”不会产生收藏卡；草稿仍可重试或手动选择。
4. 四种卡面工艺可区分；卡片保持 5:7，拖动、翻面、关闭动态均可用。
5. 删除或读取失败的照片不令收藏页崩溃。
6. `npm run build:weapp` 通过，微信开发者工具编译无页面错误；iPhone 微信真机完成拍摄、相册、揭晓、翻面与重启后读取收藏验证。

## 暂不纳入本计划

- 真实识别供应商、上传 API、服务器、账号和云同步。
- 朋友、赠送、交易、公开动态与用户实拍照片分享。
- 生产级印刷 PDF/PNG、订单和履约。
- 以 WebGL Three.js 为核心的 3D 渲染。
