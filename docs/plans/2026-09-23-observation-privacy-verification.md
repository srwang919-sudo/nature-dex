# Observation privacy hardening — local validation

- Paid recognition now uses a server-owned SHA-256(owner|observationId) receipt. Client idempotency strings cannot cause repeated provider calls. A processing receipt has a 90-second lease; expiration does not resubmit. Completed results, including failures, are replayed. A deletion tombstone blocks late completion.
- Art submission must select a candidate in that completed receipt, with matching owner, observation and original file. Only successful artwork publication writes trustedObservations in the same database transaction. No image, coordinate, place or note is in the attestation. Dynamic species remain supported; missing Latin/rarity stays empty.
- Deletion immediately revokes the attestation, even when storage deletion subsequently fails. Social reads/new copies/pending approvals check the current source attestation, not just an old share snapshot. Previously approved memorial copies remain historical non-observation records and never increase collection achievements.
- Before an upload ticket is returned, the server calls the pinned CloudBase SDK's documented getUploadMetadata and persists its fileId in assets. Only the server-derived cloudPath is returned; upload tokens/authorization/URLs are not returned or logged. Thus an upload followed by register_asset failure still has a server-owned deletion target. Registration remains backward compatible with existing owner/path validation.
- Every upload also requires a durable local observation-ID-only cleanup entry before network upload. Abandoned entries retry on launch/unload. Current observations and successfully saved cards are protected; local clear preserves outstanding abandoned cleanup intent. Cleanup now shares the exact fail-closed owner-derived deletion implementation, including rejection of storage status -1 and late-operation cancellation. A successful clear is not falsely substituted for failed deletion.
- Upload intents have a conservative separate per-owner UTC-day quota of 20 (`NATURE_UPLOAD_DAILY_LIMIT`, integer 0–100, 0 stops new intents). The earlier art=3/watercolor=3/recognition=20 controls remain. Operational values require owner budget review.

## External gates / not claimed complete

No function deployment or real provider/storage operation was performed. New recognitionReceipts and trustedObservations collections must be created and deny client direct access, and all changed functions deployed coherently. The actual CloudBase getUploadMetadata behavior and private storage rules require a controlled two-identity integration test. Historical files with no old registry cannot safely be guessed; they still require an owner-scoped inventory and cleanup. A server-scheduled retention sweep and comprehensive account erasure remain unfinished, so timestamps are not claimed as enforced retention. Client queues cannot guarantee cleanup after permanent app uninstall; server retention is mandatory before release.
